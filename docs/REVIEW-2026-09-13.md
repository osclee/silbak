Date: 2026-09-13 · Reviewer: Claude (Opus 5) with 5 Sonnet subagents · Owner: Oz
Engine version reviewed: `ENGINE_VERSION = 2` · Web at commit `91d9c4d`

> **How to use this document.** Part A is the review — what was found, with evidence, so the reasoning survives. Part B is the implementation plan — ordered phases, each with concrete steps, files, verification, and the `docs/DESIGN.md` sections that must be updated in the same change (per `CLAUDE.md`, DESIGN.md is kept in sync with generation logic, feedback semantics, and visual tokens). ## Part A — Review

### A.1 Method

- Read `docs/DESIGN.md` in full, all of `packages/engine/src`, all of `apps/web/src`, CI and deploy config.
- Played in the browser: today's daily (#256, Sunday) to a win; archive #250 to a forced loss; archive #251 keyboard-only; desktop 1024px and mobile 375×812; copy/share path; `/archive/9999`.
- Blind playtest: 3 Sonnet agents, puzzles #400–429 (30 puzzles, each weekday ~4×), via `packages/engine/scripts/playtest-cli.ts`, never seeing the solution. Prompt additionally asked each agent to log clue-wording ambiguity and bookkeeping load.
- Two Sonnet code audits: engine clue semantics / selection / tuning (730-day sweeps); web state, persistence, a11y, build.
- Every headline engine number was re-run by the reviewer (Appendix 1).

### A.2 Verdict

**The puzzle is good. The game around the puzzle isn't finished.**

Working well:
- Engine is pure, deterministic, tested, and honestly tuned. Difficulty is on target (see A.3). Testers reported genuine "aha" moments, chiefly when a clue explicitly rules out the trait-obvious favorite, and trait inversions (an elder over a prime) that the clues signpost.
- Rung selection (dark `--moss` surface + nudge) and the FLIP swap animation read clearly. Keyboard play works end to end; focus follows the ape.
- Visual identity is distinctive and coherent; token discipline (`--banana` reserved for correctness) is real.
- CI gates deploy on typecheck + tests; `dist/` and `.turbo` are not committed.

Not working:
- Feedback is a 12px glyph that vanishes the moment the player touches the board, and the history never shows what was guessed — so the core deduction loop pushes bookkeeping onto the player's memory.
- Streaks are never correct on the day they're earned; merely opening the app counts as a loss.
- Today's and any future puzzle are one URL away in the archive.
- Friday and Saturday puzzles are structurally degenerate: negative-only clue sets with zero relative-order information.
- The reveal moment (the flip DESIGN.md §6 specifies) does not exist; winning dims the board.
- No stats, no countdown, no link preview — the retention and growth loops a daily game lives on.

Themes reported independently by all three testers:
1. Glyph-only attempt history is insufficient past guess 2 — "the single biggest usability risk"; "any multi-guess deduction puzzle effectively demands a notepad."
2. All-negative clue sets (Fri/Sat) "under-constrain relative order, so early guesses lean entirely on trait heuristics… harder-because-sparse rather than harder-because-tricky." Batch 3 had four 0/6 first guesses, all on sparse-clue puzzles.
3. Best moments: a `neg` clue naming the trait favorite as "not the silverback"; `between`+`adjacent` pairs collapsing a space to two candidates.
4. Wording: "X steps aside when Y approaches" causes a beat of hesitation but was never misread. One tester over-read "Enzi is not the silverback" as "Enzi ranks low" and lost a guess. One tester read `between` as *not* specifying which endpoint is higher (see A.4 #6).

### A.4 Findings

Severity: **P0** = fix before anyone else plays · **P1** = the game around the puzzle · **P2** = hygiene.

#### P0

**1. Attempt history doesn't show what you guessed.**
`apps/web/src/components/AttemptsHistory.tsx` renders `#1 ■■○○■○` from `entry.feedback` only; `entry.arrangement` is never read. Binary feedback makes Silbak a position-elimination game ("Kanzi was wrong at rung 3 in guess 2"); without the arrangement the player cannot do the elimination without paper. Wordle keeps the letters in the grid for exactly this reason.

**2. All feedback vanishes on any swap.**
`apps/web/src/components/Ladder.tsx` gates every glyph on one boolean, `arraysEqual(lastEntry.arrangement, arrangement)`. Verified in-browser: three `■` marks disappeared when two *other* rungs were swapped. The player must memorize which rungs were correct before touching anything. Compounds #1.

**3. Today's and future puzzles leak via the archive.**
`apps/web/src/routes/Archive.tsx` lists today; `apps/web/src/routes/ArchivePuzzle.tsx` validates only `n >= 1`. Verified: `/archive/256` is today's puzzle with unlimited, unpersisted retries; `/archive/9999` renders 2053-05-17 with real clues and solution; `/archive/99999999999999` throws inside `Date#toISOString` with no error boundary — white screen.

**4. Streaks are never correct on the day you win; opening the app counts as a loss.**
`submit()` in `apps/web/src/state/useGameStore.ts` never touches `streak` or `played`; only `applyRollover()` does, on the *next day's* `load()`. Verified after winning today: `streak.count: 0, played: {}`. Separately, `load()`'s no-current branch persists `current = {status: "playing", history: []}` on first open, so a day that was opened but never played rolls over as `solved: false` and resets the streak — indistinguishable from a loss. `streak.max` is threaded to `ResultCard` and dropped; `played` is never read anywhere.

**5. Friday and Saturday puzzles are structurally degenerate.**
Measured over 730 generated days (Appendix 1): Saturday lands on `space = 480` (59×) or `504` (45×), always exactly two `neg` clues, nothing else. Friday is `neg`-only too (3–4 clues; spaces 288/312/336/360). This is the same lattice trap `packages/engine/src/select.ts` documents fixing for Friday — the fix diversified the *count* but not the *kind*, and Saturday was never fixed. Mechanism: at Saturday's ceiling (504) `DOMINANCE_MARGIN` empties the non-dominant pool, so selection falls back to the full pool; but the floor (360) equals the solo-survivor count of `order`/`half`, so any relational first clue lands *at* the floor and any second clue pushes under it — only `neg` pairs survive, and inclusion-exclusion gives exactly {480, 504}. Two further claims in the code are false in practice: the `bestInBand`/`nearest` fallbacks never fired in 730 days, and "reliably lands exactly on 504" is 45%. The existing band-adherence test checks membership in `[floor, ceiling]`, not diversity, so it cannot catch this class of bug. Net: 29% of puzzles — the weekend — carry zero relative-order information, which is what testers described as guesswork.

**6. The `between` clue is stronger than it reads.**
`packages/engine/src/clues.ts` tests `rank(x) < rank(y) < rank(z)` strictly — 120 of 720 survive. The text "Y ranks somewhere between X and Z" does not tell an English reader which of X/Z is higher; the symmetric reading leaves 240. A tester explicitly adopted the symmetric reading. 78% of Sundays (168/214) carry at least one `between` clue, so the engine's reported `space` understates the player's real search on the "soft landing" day by up to 2× per clue. This is the one clue that violates DESIGN.md §4's own phrasing rule ("clarity beats flavor whenever flavor could change the parse").

#### P1

**7. The reveal has no ceremony.**
DESIGN.md §6 Motion: "on submit, rungs flip on X with an 80ms stagger, then feedback lands." Not implemented — no keyframes exist outside `CanopyScene`. Submit instantly changes a 1.2rem glyph at the rung's far right; the rung surface never changes; and because rungs are `disabled` after the game ends, `.rung:disabled { opacity: 0.75 }` **dims the whole ladder on a win** — victory reads as "inactive."

**8. No stats, no countdown, no distribution.**
The result card is headline + emoji grid + copy button. `played` and `streak.max` are persisted and never rendered. No "next troop in hh:mm."

**9. Sharing and link previews.**
Share text has no URL (DESIGN.md §5 is line-1-only by design — recommend reconsidering; it's how Wordle clones grew). No OG/Twitter meta, no favicon, `apps/web/public/` is empty. `apps/web/index.html` description still says "Rank **five** apes"; `theme-color` is `#0D1913`, the retired dark palette, so mobile browser chrome is near-black over a cream page.

**10. Rules and onboarding gaps.**
`apps/web/src/routes/About.tsx` never defines the clue idioms ("groom below", "steps aside when … approaches", "no one ranks in between"), doesn't list the silvering (none/flecked/part-silver/full) or build (slight/solid/heavy) tiers, has no worked example. The in-game rules line never says silverback = top. Nothing says a negative note excludes only that one rung (a tester lost a guess to this). `count` clues at the extremes — "0 of the troop groom below X" / "5 of the troop groom below X" (3% of puzzles) — are the most decisive clue in the game phrased as a riddle. The Rules page renders `■` in `--forest` while the game renders it in `--banana`.

**11. Mobile layout.**
At 375×812: first rung at y = 402; the `12ch` rank column (`Rung.module.css` grid) is 96px — 25% of the viewport — to display "02"; trait lines wrap to 3–4 lines so rung heights vary 82–114px; page is 1.7 screens; Submit is below the fold. A game about comparing six things should show all six and the submit button at once.

**12. Smaller loop issues.**
- The same arrangement can be resubmitted with no warning (verified: six identical submits).
- Loss reveal is a text list under the ladder still showing the player's wrong order.
- Archive list: no dates/weekdays, no played/solved markers, "Silbak epoch: 2026-01-01" is a developer detail on a player page, list is a nested `max-height: 60vh` scroll region, hover adds a 1px border that shifts layout. Nav has no active-page state.

#### P2

- **A11y:** DESIGN.md §8 claims a per-guess `aria-live` announcement ("Rung 3 correct, four rungs wrong"); only `ResultCard` has a live region, so guesses 1–5 announce nothing. `Ladder.tsx` puts `role="list"` on a div whose children are `<button>`s (no `listitem`). `Legend` is `aria-hidden` with no screen-reader equivalent.
- **Bundle:** 680KB of the 941KB deploy is `@fontsource` Cyrillic/Greek/Vietnamese subsets (50 font files) pulled by unqualified `@import` in `global.css`, for an English-only game.
- **State:** `Daily.tsx` calls `load(todayKey())` once on mount, so an open tab never rolls over at midnight. `deviceId` and `prefs.*` are write-only. `MAX_GUESSES` is `6` in the store and a literal `6` in `Board.tsx`. `Board.tsx` subscribes to the whole store without a selector (harmless today).
- **Config:** `staticwebapp.config.json` references `/api/profile` (no API exists) and excludes `*.png/webmanifest` that are never produced.
- **DESIGN.md drift:** the flip animation, the live region, the "nearest miss" fallback, and "reliably lands on 504" all describe things the code does not do. The doc is unusually good; keep it honest.
- **Brand:** "Karisoke" (the eyebrow line) is the Dian Fossey Gorilla Fund's real research center. Flavor now; a conversation before launch.
- **Portraits:** at 56px, silvering and build read; age and scar mostly don't. Fine — text labels carry them — but DESIGN.md §6's "read a rung before reading its label" isn't met for those two.
- **Tuning note (no action yet):** trait-favorite = silverback 64% (target 55–65%, at the edge). That metric covers rung 1 only. With `NOISE = 4.4` uniform, apes whose trait scores sit within ~1 point of each other are effectively shuffled — archive #250's bottom three (3.2–3.6) landed in trait-inverse order. Pure trait-sort yields ≥3 exact rungs only 48% of the time, 0 exact 6.5%. Worth a second target metric before NOISE is ever touched.

## Part B — Implementation plan

Conventions for every phase:
- Run `pnpm typecheck && pnpm test` from the repo root before and after.
- Verify UI changes in the browser via the `silbak-web` preview config (`.claude/launch.json`), desktop and 375px mobile.
- Update the listed `docs/DESIGN.md` sections in the same change. Add a changelog line at the top of DESIGN.md (`v0.9` for the first shipped phase, etc.) explaining *why*, matching the existing style.
- Engine changes that alter emitted puzzles: pre-launch, bump `ENGINE_VERSION` in `packages/engine/src/version.ts` (per `CLAUDE.md`), then `rm -rf packages/engine/test/__snapshots__` and re-run tests to regenerate the golden snapshot deliberately. Never regenerate the snapshot to silence a failure you don't understand.
- Do not touch `NOISE`, `DOMINANCE_MARGIN`, or `BANDS` outside Phase 3, and there only with a sweep.

### Phase 1 — Make the board support deduction (P0 #1, #2, P1 #12 duplicate-submit)

**Why first:** unanimous tester feedback; zero engine risk; largest felt improvement per hour. These three changes are all in the board loop and should ship together.

1. **Keep feedback on unmoved rungs.** In `apps/web/src/components/Ladder.tsx`, replace the single `showFeedback` boolean with a per-index check: rung `i` shows `lastEntry.feedback[i]` iff `lastEntry.arrangement[i] === arrangement[i]`. Rungs that have moved since the last graded arrangement show no glyph (optionally a muted "moved" marker in `--mist`; do not use `--banana`). Keep `key={apeId}` so the FLIP swap still works.
   - Verify: submit, swap two `wrong` rungs, confirm the `exact` rungs keep `■`.
   - DESIGN.md: §2 "Feedback is per-position" — add a sentence that feedback persists on a rung until that rung's occupant changes.

2. **Show arrangements in attempt history.** In `apps/web/src/components/AttemptsHistory.tsx`, render each entry as a row of six cells; each cell shows the ape and the glyph. Portraits are not legible below ~46px (DESIGN.md §6) and six of them won't fit a 375px row with the chip padding, so use a short name form — first 3–4 letters in `--font-mono`, or the full name if the row is a grid that wraps — with the glyph beneath or beside it. `--banana` on `--bark` chips already exists for `exact`; keep it. Consider (optional, stretch) a per-ape summary line derived from history: "Kanzi: not 2, not 4".
   - Verify: after 3 guesses the history shows, for each guess, which ape sat on each rung and its result; at 375px nothing overflows horizontally.
   - DESIGN.md: §7 screens diagram ("ATTEMPTS (compact chips)") — update to describe the row format and why (binary feedback makes past arrangements load-bearing).

3. **Block resubmitting an unchanged arrangement.** In `apps/web/src/components/Board.tsx`, disable the submit button (and set the hint row text to "Change something first") when `history.length > 0` and `arraysEqual(history[history.length-1].arrangement, arrangement)`. Also guard in `submit()` in the store so the keyboard path can't bypass it.
   - Verify: after a submit, the button is disabled until a swap happens.

4. Unify `MAX_GUESSES`: export it from the store (or from the engine) and use it in `Board.tsx` instead of the literal `6`.

### Phase 2 — Fix persistence and the archive (P0 #3, #4; P2 state items)

**Why:** correctness bugs in the only retention mechanic and a spoiler leak. No design decisions needed.

1. **Streak/played in `submit()`.** In `apps/web/src/state/useGameStore.ts`, when `nextStatus !== "playing"` and `!isArchive`: write `played[puzzle.number] = { guesses, solved }`, and update `streak` immediately — `count = solved ? (lastPlayedKey === yesterdayKey(dateKey) ? count + 1 : 1) : 0`, `max = Math.max(max, count)`, `lastPlayedKey = dateKey`. Set the store's `streak` from this so `ResultCard` shows today's number.
2. **Rollover must not record unplayed days.** In `applyRollover`, if `current.history.length === 0`, drop `current` without writing `played` or touching `streak`. (A player who never submitted did not lose; whether a *missed* day breaks the streak is already handled by the `yesterdayKey` check on the next win.) Keep `applyRollover` as the safety net for a day that was played but whose terminal submit predates this change.
3. **Don't persist `current` on first open.** Either persist only from the first `submit()`, or keep persisting but make step 2 the guard. The first is cleaner.
4. **Midnight rollover in an open tab.** In `apps/web/src/routes/Daily.tsx`, re-check `todayKey()` on `visibilitychange`/`focus` (and optionally a 60s interval) and call `load()` if it changed. `load()` already handles rollover.
5. **Archive clamp.** In `ArchivePuzzle.tsx`: compute `current = puzzleNumber(todayKey())`; if `n >= current` → `<Navigate to="/" replace />` for `n === current`, `/archive` otherwise. Guard non-integer and absurd values (`!Number.isInteger(n) || n < 1 || n > 100000`) before calling `dateKeyFromPuzzleNumber`. In `Archive.tsx`, list from `current - 1` downward. Add a top-level React error boundary in `App.tsx` that renders a plain "Something went wrong — reload" panel.
6. **Surface `played` in the archive list.** Each row: puzzle number, date and weekday (helps players learn the difficulty ladder), and a `🍌 3/6` / `🪨 X/6` marker from `played[n]` if present. Remove the "Silbak epoch" line. Let the list flow in the page instead of a nested scroll region. Fix `.link:hover` to not shift layout (reserve a transparent border).
7. Remove `deviceId` and `prefs` from `Persisted`, or leave them with a comment that they're reserved — but stop pretending they're used. If the shape changes, keep `v: 1` and tolerate missing fields; a wipe is acceptable pre-launch but unnecessary.
   - Verify (manual, with DevTools → Application → Local Storage): win → card shows `🔥 1 day streak` immediately; reload → still 1; clear `current`, set `lastPlayedKey` to yesterday, win → 2; open the app, don't play, advance the clock → no `played` entry, streak unchanged. `/archive/<today>` redirects to `/`; `/archive/9999` and `/archive/99999999999999` redirect to `/archive` without a crash.
   - DESIGN.md: §9.5 streak semantics — resolve it ("archive is practice; streak = consecutive daily wins, updated at the terminal submit; an opened-but-unplayed day is neither a win nor a loss").

### Phase 3 — Fix weekend generation (P0 #5, #6; P2 tuning note)

**Why:** 29% of puzzles carry no relational information, and one clue kind is mis-scored. This phase changes emitted puzzles, so it bumps `ENGINE_VERSION` (2 → 3) and regenerates the snapshot. Do it as one engine change so the version bumps once.

1. **Reword `between`.** In `packages/engine/src/clues.ts`, change the text to make direction explicit, e.g. `` `${name(y)} ranks below ${name(x)} but above ${name(z)}.` `` Keep the strict predicate. (Alternative considered and rejected: make the predicate symmetric — that weakens the clue to 240 survivors and reshuffles every band; rewording keeps the strong clue and removes the ambiguity, which is what §4's phrasing rule asks for.) Update the clue table in DESIGN.md §4.
2. **Reword extreme `count` clues.** When `count === n - 1` emit "X is the silverback." and when `count === 0` emit "X holds the lowest rung." — same predicate, same kind. These are already giveaways; they should read like ones.
3. **Require at least one relational clue.** In `packages/engine/src/select.ts`, treat a chosen set as invalid unless at least one clue has `kind ∈ {order, adjacent, between, half}`. Simplest placement: in `attemptSelect`, don't stop at `MIN_CLUES` unless the set contains a relational clue; and in `selectClues`, reject `inBand` results that lack one. Keep `neg` available — testers loved "X is not the silverback" when it names the favorite — just never as the *only* information.
4. **Re-sweep Friday and Saturday bands.** With step 3 in place, `[360, 504]` is unreachable by construction (an `order`/`half` clue alone leaves 360; adding anything drops below the floor). Use `packages/engine/test/difficulty-simulation.test.ts` to sweep candidate bands and pick ones where (a) the generator lands in-band and irreducible on the primary pool for ≥95% of days, (b) `space` takes ≥4 distinct values per weekday, (c) at least two clue kinds appear across the weekday's puzzles, (d) Knuth-optimal guesses-to-solve still rises Mon → Sat. A reasonable starting hypothesis: Fri `[225, 300]`, Sat `[288, 400]` — but sweep, don't guess. If the difficulty ceiling drops, that is acceptable: the doc's own numbers show optimal-solver guesses only climb from ~1.8 to ~3.3 across the entire range, so the top bands were buying little difficulty at a high cost in clue quality.
5. **Add a diversity invariant test** (`packages/engine/test/invariants.test.ts` or a new `diversity.test.ts`): for each weekday over ≥100 sampled dates, assert `new Set(spaces).size >= 4` and that the union of clue kinds contains at least one relational kind for *every* puzzle. This is the test that would have caught both the documented Friday bug and the Saturday one.
6. **Fix the stale claims** in the `BANDS` comment in `select.ts` ("reliably lands exactly on 504", "diverse again") and in DESIGN.md §4 (fallback paths that never fire — either delete the fallback code or note it as a safety net that has not been observed to trigger).
7. Bump `ENGINE_VERSION` to 3 with a comment explaining why (relational-clue requirement + band re-sweep + clue rewording). Regenerate the determinism snapshot. Re-run `model-tuning.test.ts` and `trickiness.test.ts` — they should pass unchanged, since `NOISE` and troop generation are untouched.
8. **Playtest** with `.claude/skills/playtest-puzzles/SKILL.md` (75 puzzles, 5 agents, fresh puzzle numbers ≥ #500). Compare against this review's 30-puzzle table and the 75-puzzle baseline (avg 2.17). Success looks like: similar average, ≤5% needing 4+ guesses, and the "feels like guesswork" note gone from the Fri/Sat puzzles.
9. **Tuning follow-up (optional, after 1–8 ship):** add a second target metric to `model-tuning.test.ts` — expected number of exact rungs from a pure trait-sort guess (currently: ≥3 exact 48%, 0 exact 6.5%). Document the target in DESIGN.md §3 next to the existing 55–65% silverback target. Do not change `NOISE` until that metric exists.
   - DESIGN.md: §4 clue table (new `between`/`count` wording), §4 difficulty bands table (new Fri/Sat values and the relational-clue rule with the mechanism from A.4 #5 recorded as a documented trap), changelog entry.

### Phase 4 — The reveal and the result (P1 #7, #8)

**Why:** this is the emotional beat of the game and the retention loop. Pure web work.

1. **Flip on submit.** Add a CSS keyframe to `Rung.module.css` (rotateX 0 → 90 → 0, ~400ms) applied via a class the `Ladder` toggles for the render after a submit, with `animation-delay: calc(var(--i) * 80ms)` per rung index. Feedback glyphs and the rung tint (step 2) should appear at the 50% point of each flip, not before. The global `prefers-reduced-motion` rule in `global.css` already collapses CSS animations; no extra opt-out needed (unlike the WAAPI swap).
2. **Tint the rung on `exact`.** Don't rely on the glyph alone: give `.rung.exact` a `--banana` ring (`box-shadow: 0 0 0 2px var(--banana)`) or a `color-mix(in srgb, var(--banana) 18%, var(--card))` surface. Check the selected-rung contrast test in DESIGN.md §6 ("select a rung that is showing `■` and look at it") still holds. `--banana` is reserved for correctness — this *is* correctness, so it's the one legitimate new use.
3. **Don't dim on win.** Split "game over" from `disabled`: keep rungs non-interactive after the game ends but don't apply `opacity: 0.75` when `status === "won"`. Consider a one-shot celebration (the full ladder flipping gold in sequence is probably enough).
4. **Stats panel** in `ResultCard.tsx`: played, win %, current streak, max streak, and a 6-bar guess distribution computed from `played` (which Phase 2 makes reliable). Highlight today's bar.
5. **Countdown** to the next puzzle: local midnight (`todayKey()` is local, so the countdown must be too), rendered as "Next troop in hh:mm", updating each minute.
6. **Loss reveal:** animate the ladder into `revealOrder` (reuse the FLIP machinery in `Ladder.tsx` — measure, reorder, animate) instead of, or in addition to, the text list.
   - Verify: reduced-motion emulation shows feedback instantly; win state is not dimmed; stats match localStorage; countdown hits 00:00 at local midnight.
   - DESIGN.md: §6 Motion (describe what was actually built), §6 Tokens (`--banana` now also tints the correct rung — note it), §7 result state.

## Appendix 1 — Reproducing the weekend finding

Run from `packages/engine/` (`npx tsx <file>`); takes ~1 minute.

```ts
import { generate } from "./src/index";
const hist: Record<number, Record<string, number>> = {};
const start = Date.UTC(2026, 0, 1);
for (let i = 0; i < 730; i++) {
  const d = new Date(start + i * 86400000);
  const key = d.toISOString().slice(0, 10);
  const p = generate(key);
  const sig = `${p.space}|${p.clues.length}|${[...new Set(p.clues.map(c => c.kind))].sort().join(",")}`;
  (hist[d.getUTCDay()] ??= {})[sig] = ((hist[d.getUTCDay()] ??= {})[sig] ?? 0) + 1;
}
for (const dow of [0, 1, 2, 3, 4, 5, 6]) {
  const rows = Object.entries(hist[dow]).sort((a, b) => b[1] - a[1]);
  console.log(["Sun","Mon","Tue","Wed","Thu","Fri","Sat"][dow],
    new Set(rows.map(r => r[0].split("|")[0])).size, "distinct spaces");
  for (const [sig, n] of rows.slice(0, 5)) console.log("  ", n, sig);
}
```
